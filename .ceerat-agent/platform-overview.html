Backend domains

Account resolution, customers, catalog, carts, orders, careers, calendar, preferences, AI threads, and administration remain behind service-owned APIs. Consult current Go declarations and inventories for exact methods.

Customer profiles own shipping/billing addresses. Catalog APIs own products and carts. Order APIs own checkout and order transactions. Career APIs own job and resume workflows.

Data and search

PostgreSQL is authoritative for operational business records. Typesense is derived search infrastructure managed by backend services; browsers and AI callers do not write its indexes directly.

Gateway confirmation, connection, and audit storage is separate from backend business records. It does not authorize direct gateway writes to customer or order tables.

03 / Security

Authentication does not grant business access

  1. Keycloak authenticates the person. It owns passwords, recovery, email verification, and social identity linking.
  2. The caller validates its entry point. Browser portals enforce their session rules; the public gateway validates its OAuth resource audience, client, and tool scopes.
  3. The backend validates the original access token. It checks signature, issuer, API audience, approved client, lifetime, subject, and exact method scopes. It resolves verified issuer/subject identity to the Ceerat account.
  4. RBAC and ownership authorize the operation. Role and account status determine access; handlers and repositories constrain records to the authenticated owner.
Portal session boundaries
PortalRequired accountPurpose
Customer UIActive customer with an owned customer profileCustomer self-service
Admin UIActive adminUsers, roles, RBAC, administration
Agent UI (ceerat-web-ui)Active agent or admin; agent registration starts pendingOperational workflows and agent/admin chat
Preserve the credential boundary. Forward the original Keycloak access token only to the designated service. Do not mint a second end-user JWT, exchange caller-supplied identity for access, or add password API fallbacks. HttpOnly cookies prevent JavaScript from reading the token; the browser still transports the cookie.

Do not put tokens, cookies, OAuth codes/state/verifiers, passwords, or private keys into model prompts, public responses, or logs. Keep sanitized failure-stage diagnostics server-side. A role or owner supplied in a request is not authority.

04 / Deployment

Verify the backend connection before accepting traffic

Render public HTTPS and private backend TLS are separate connections. Each production client must trust the CA that signed the backend certificate and verify its server name. Private networking alone provides neither authentication nor certificate trust.

GET /healthz · Liveness

The portal process can respond. This stays independent of downstream availability and does not establish that login or backend calls work.

GET /readyz · Transport readiness

Each portal opens a fresh gRPC connection with its configured TLS credentials, completes TLS and HTTP/2 handshakes, and closes the probe connection. Success returns 200; failure returns generic 503 within two seconds.

The Render Blueprint uses /readyz for customer, admin, and agent portals. A cached gRPC Ready state is insufficient. Gateway and agent-service health endpoints do not automatically inherit this behavior.

Why the certificate mismatch broke login

The customer portal could not verify the user service certificate and logged x509: certificate signed by unknown authority. It displayed an account-required message even though transport failed before account validation. Correcting the CA restored login. A process-only health check had not detected the mismatch.

Provisioning and rotating certificates
  • render.yaml specifies paths; Render secret files provide contents. Setting /etc/secrets/ceerat-grpc-ca.pem does not upload or synchronize that file.
  • Clients need the public CA certificate. Keep backend private keys and CA signing keys outside Git and out of client deployments. A PEM extension alone does not indicate a secret.
  • A shared CA-only environment group is the recommended distribution pattern; it has not been established here as a verified deployment fact.
  • Reuse signing material on routine deployment. For CA rotation, distribute overlapping trust first, redeploy clients, rotate the server certificate, verify fresh connections, then remove old trust and redeploy.
  • Monitor expiry separately. Never fix trust failures by disabling TLS verification.

Readiness is a transport check, not an OAuth, database, or end-to-end business test. Backend outages also make running portals unready; account for the hosting platform’s health-check policy. Keep local test results, pushed commits, live rollout, and successful login as separate evidence.

05 / Documentation

Read the checkout, not a session-memory snapshot

The builder loads fresh go list and go doc output for each plan. These commands read the same package comments and declarations rendered by pkgsite. A running documentation server is optional for planning.

Source facts

Go package and declaration comments own API names, signatures, fields, and package responsibilities. Generated APIs derive from proto source. Inventories help discovery; current declarations take precedence for API facts.

Architecture and policy

Markdown standards own security rules, service boundaries, and operational decisions. Update them when policy changes. If source and policy disagree, report the discrepancy; do not silently weaken the policy.

# Run from ceerat-platform-builder-agent
ceerat-builder go-docs "customer profile" --output json
ceerat-builder go-docs \
  --package github.com/kaansari/ceerat-contracts/proto/customer \
  --symbol CustomerProfilePatch --output table
ceerat-builder plan "update customer profile" --output json
ceerat-builder check-context

Both local packets and AI context receive the fresh docs. Local packets use source_evidence with category current_go_documentation. Each result includes source paths, a documentation SHA-256, a pkgsite link, and truncation status.

Selection, limits, and failure handling

The loader considers canonical contracts, the user service, gateway, private agent service, and all three portals. It selects up to eight packages by request relevance and includes up to 12,000 documentation characters per package. Missing checkouts and truncated output are explicit. Use package/symbol lookup when more detail is needed.

Each Go command has a 30-second timeout. Module resolution is readonly and offline; dependencies must already be available. Missing Go or an unusable workspace causes an actionable error, not a fallback to old session notes. Source documentation is not proof of live deployment.

Set up the workspace and browse package docs

Run from the parent containing the sibling repositories. For a new workspace only:

go work init \
  contracts-repo/packages/ceerat-contracts \
  services-repo/services/ceerat-user-service

Extend an existing workspace without deleting other entries:

go work use \

go install golang.org/x/pkgsite/cmd/pkgsite@latest

06 / Planning

Discover → decide → verify

  1. Discover the current owner. Read fresh package docs, then inspect contracts and inventories. Do not infer that a missing search result means a capability is absent.
  2. Choose the smallest service change. Reuse existing RPCs when appropriate. Keep backend persistence, identity, scope, and ownership rules explicit. App and AI changes are integration impact for this services-focused builder.
  3. Verify behavior at the relevant boundary. Run focused tests, contract generation checks, inventory drift checks, and deployment probes where applicable. A green documentation command is not an application test.
  4. Maintain the right source. Update package comments and proto source with code. Update architecture/security policy only for changed boundaries or rules; do not copy API declarations into session-maintained summaries.
